# The roadmap index is generated

*Name: provisional (a lane ships names provisionally; calef names things). `roadmap-index` is the
noun for the thing the note is about, and it sits beside `notes/merge-queue.md` and
`notes/naming.md` as a note about the machinery rather than about the kernel.*

`design/roadmap/README.md`'s milestone table is **derived from the block files** and regenerated by
`script/roadmap --write`. Nobody edits it by hand. This note is the argument for that, the method
the migration used, and the parts a gate cannot check.

Milestone 294 is the block; this is the part a reader needs when they are holding the problem
rather than reading the history.

## The task: add a milestone to the roadmap

You are a lane, you have been given milestone `N`, and you want a row in the index.

1. Write `design/roadmap/N-<slug>.md` as usual: `# N. <title>` on line 1, `**Status: <TOKEN>` in
   the paragraph under it, `**Gate: <spec>.**` in the paragraph under that unless the status is
   `BUILT` or `REMOVED`.
2. Give it a `## Index row` section, conventionally last, beside `## Follow-on` and `## BUGS`:

   ```markdown
   ## Index row

   **Built:** 2026-09-14

   One paragraph saying why this milestone matters, which is what the index table shows in its
   `Why it matters (§14)` column. Drop the `**Built:**` line unless the status is BUILT or
   REMOVED; every other status carries no date.
   ```

3. **Do not touch `design/roadmap/README.md`.** Your row is minted when the index is regenerated,
   the same way every other thing that is global to this tree is minted at merge.
4. `script/roadmap --check` will tell you the index is stale by one row. That is correct and is not
   your defect.

### EXAMPLES

```console
$ script/roadmap --index | head -3            # the table as the blocks currently say it
$ script/roadmap --write                      # rewrite it into design/roadmap/README.md
roadmap: rewrote 289 rows in design/roadmap/README.md
$ script/roadmap --check                      # validates the blocks; reports index staleness
roadmap: 289 milestones, 291 files, status vocabulary clean, every '## Index row' parses, ...
roadmap: the committed index matches all 289 blocks
```

A lane that has just added a block sees the other half of that line instead:

```console
$ script/roadmap --check
roadmap: the committed index is STALE in 1 of 289 rows: 1 not in it yet (294). Run
`script/roadmap --write` (the integrator does this at merge)
```

## Why: the index table was the tree's worst merge hotspot

Measured on 2026-09-14, in one session: **eight merge conflicts, every one of them in
`design/roadmap/README.md`'s index table and zero anywhere else.** Pull requests #836, #843, #847,
#849, #850, #851, #854 and #855, several more than once, because `main` moving even once
re-conflicted every open lane.

It was structural. `script/lint` check 4b requires every lane to touch its own milestone's block;
every milestone also needed a row in one sorted table; so **every milestone in flight collided with
every other milestone in flight, always, in that one file.** `AGENTS.md` names
`kernel/src/user/tests.rs` as the hotspot to fear, measured on 2026-08-16, and that is the wrong
file: only some lanes wire a test, and every lane adds a row.

The strongest argument is that `script/roadmap` exists because of this table. Its header records
that milestone status used to be prose phrased a dozen ways, that a sweep mis-reported eight
milestones, and that *"milestone 69's row said NOT-STARTED while its block said BUILT"*. One of its
checks was that the row and the block must agree. Generating the row makes that check vacuously
true, which is rung one of `AGENTS.md`'s ladder where the gate was rung two.

## The two columns that had to move, and the measurement that decided it

Three of the five columns were already derivable: the number is the filename's, the status is the
`**Status:` line the script already read, the title is the H1 it already read. The other two were
not, and both options for avoiding a migration were measured before they were refused.

**Deriving the summary from the block's opening paragraph.** Refused on evidence. Across 288
milestones the row's summary scored a **median similarity of 0.07** against the block's first body
paragraph; three scored above 0.4 and none above 0.6. An opening paragraph is written to open a
document rather than to summarise one. Taking it would have rewritten what the index said about 288
milestones in a single commit, and those cells are the tree's own account of its history.

**Reading the Built date out of the status sentence.** Refused on evidence. **129 of 288** blocks
did not state the date anywhere a parser could find it, and the ones that did used at least eight
spellings:

```
**Status: BUILT.**                                    (the date only in the index)
**Status: BUILT, 2026-08-26.**
**Status: BUILT (2026-08-01).**
**Status: BUILT** 2026-09-14.
**Status: BUILT** (2026-08-03).
**Status: BUILT** on 2026-08-18 (PR #320).
**Status: BUILT**, 2026-08-27, as `rmle` rather than ...
**Status: REMOVED 2026-08-30.** Built 2026-08-17, and ...
```

Canonicalising 129 status lines is rewriting prose in 129 blocks to serve a parser, which is the
wrong direction and is not a thing a lane may do.

**Generating only the derivable columns and leaving the summary in the table** was the third
option, and it solves nothing: a lane would still edit one shared file to add its summary, so the
whole conflict class survives and the milestone would not have paid for itself.

### Would we still choose this if both options cost the same?

Yes, and it is worth answering out loud because the chosen option is **much** the most expensive
of the three: it migrated 288 files where deriving from the opening paragraph would have migrated
none. The reason is not effort in either direction. Deriving would have changed what the index says
about 288 milestones, silently, in the direction of text that was never written to be a summary.
Moving text is safe; regenerating it is not.

## The method, and why the proof is reconstruction

The migration cut each cell's text and pasted it into its block. **Two transformations only**, both
of which round-trip exactly: `\|` was unescaped (a bare pipe would end a table cell, so the table
escaped it; in prose it is an ordinary pipe), and the paragraph was wrapped to 98 columns, with any
wrapped line that would have started with a markdown-significant character folded back into its
predecessor.

**The proof is that the table regenerates.** Generating from the migrated blocks and diffing
against the committed table reproduced **271 of 288 rows byte for byte**. All 17 differences were
pre-existing drift in the hand-maintained table:

- **12 whitespace.** Eight rows carried a doubled space in an empty `Built` cell (131, 224, 258,
  260 through 263, 265); four padded the date (135, 196, 202, 208). Invisible in rendering and
  invisible to the old gate, which anchored on the first four fields.
- **5 titles** where the row had drifted from its own block's H1 (16, 29, 47, 48, 121), now
  resolved in favour of the block. `script/roadmap`'s header used to excuse these as rows
  abbreviating on purpose; two of the five abbreviations had dropped the backticks off command
  names, which is a loss rather than an abbreviation.

**Verify by reconstruction, not by inspection**, is the transferable part. A 288-file migration
cannot be read. It can be proved, by regenerating the thing it came from and diffing, and the diff
is worth more than the migration: it found drift nobody was looking for.

## What the gate does now, and the one thing it deliberately stopped doing

`script/roadmap` reads the **blocks** for status, gates, follow-on dispositions and tree-wide
citation resolution. All four used to key on the index table, which is why a block with no row used
to fail everything.

**A committed row that disagrees with its block no longer fails the build**, and this is the
deliberate part. The milestone-69 defect was real *because both records were hand-maintained and
both looked authoritative*: a reader could not tell which was lying. Once the row is derived there
is nothing to decide. A table that disagrees with a block is stale, the fix is one command, and
`--check` reports it with the count and the command and passes.

It has to pass. Failing would force every lane whose status moves to regenerate, which means
editing the table, which is the hotspot coming back.

## BUGS

- **The committed table can be stale, and nothing fails when it is.** Between a merge and the
  integrator running `script/roadmap --write`, the table is behind the blocks. Detection is rung
  two (the count and the command print on every `--check`, which every `script/lint` run makes);
  the action is rung four. `AGENTS.md` asks for an exception like this to be declared rather than
  left to read as a design, so: this is one, and it is a foot gun for anyone who reads the
  committed table as authoritative. **`script/roadmap --index` is authoritative; the table is a
  rendering.**
- **Three higher rungs were looked at and each cost more than the staleness does.** A bot pushing
  the regeneration to `main` would race the merge queue and can evict it, and this tree's own
  convention is that a scheduled job must never push to `main` (`.github/workflows/metrics.yml`
  says so in its header). A `merge=union` attribute on the table would auto-resolve the append
  conflicts and leave the rows mis-sorted, trading a visible conflict for a quiet wrong answer, and
  it would introduce `.gitattributes` semantics nothing else in this tree uses. Failing the gate on
  a stale table brings the hotspot back.
- **`## Index row` is a provisional name.** `## Summary` is the generic word this tree's naming
  tenet warns against, and `## Why it matters` was unavailable: **13 blocks already carry one**,
  holding a different kind of text (the argument for the milestone's importance, not the precis the
  table shows), and reusing the heading would have meant merging two distinct texts in 13 files,
  which is a judgement call a mechanical migration may not make.
- **The section is one paragraph, and a gate enforces that.** A table cell is one paragraph, so a
  section that could hold three would make the generator choose which one the index shows. The cost
  is that a block whose summary genuinely wants two paragraphs cannot have one; none of the 288 did.
- **`script/metrics` reads the committed table, not the blocks.** Its milestones chart counts
  `design/roadmap/README.md`'s rows at each week's revision, which is one blob instead of 290, and
  that is the right trade for a series that walks the whole history. The cost is that a week counted
  while the index was stale undercounts by however many milestones landed since the last
  regeneration. It self-corrects on the next one, and past weeks are read from their own revisions.
- **Two lanes minting the same milestone number still collide.** What changed is the shape: it is
  now two files claiming one number, which `script/roadmap` has always called fatal and which
  `script/decisions` records as the reason a directory beats a single file, rather than two rows in
  one table.
