1. **kernel/src/user/install_service.rs — `format_disk_description` reports MBR and backup-GPT disks as "unpartitioned or unreadable".** The function only recognises partitions via `F_PRIMARY` (a valid primary GPT). The commit defines `F_MBR` and `F_BACKUP`, so the surveyor detects those cases, but the formatter never consults them: a disk carrying an MBR partition table — the most common Windows/Linux layout a user will actually meet, and the exact case the cited proposal exists to warn about — falls through to " (unpartitioned or unreadable)". The module's own docs call this sentence "the single most load-bearing sentence a stranger reads"; as written it actively tells a person that a partitioned disk is empty right before they type INSTALL.

2. **kernel/src/user/install_service.rs — `spawn_surveyor` can never return `None`, so the failure path is a lie and real failures hang the boot.** Every path through the function ends in `Some(...)`; there is no timeout anywhere, just two blocking `ipc_recv`s. If the surveyor crashes, sends only one message, or one of the `expect`s inside the spawned closure panics in the child thread, the boot blocks forever before the prompt is ever printed — silently, on exactly the headless-machine scenario the module docs address with "The wait is bounded, so a stick booted on a machine with no console reaches the prompt instead of hanging." The " (survey timed out or failed)" branch and message are dead code promising failure handling that does not exist.

3. **kernel/src/user/install_service.rs — the `F_NIFE` branch is dead code that resolves a two-survey disagreement in the destructive direction.** `offer()` has already returned when the installer's `ROLE_SURVEY` reports `R_ALREADY`, so the surveyor can only report `F_NIFE` if the two surveys disagree — and in that case the code prints "(already has nife installed)" and still offers to wipe the disk, rather than refusing. If the surveyor is meant to supersede the installer survey, the old spawn should be deleted; as written, every stick boot pays for two disk-probing processes whose verdicts can conflict, and the conflict is resolved by asking the user to destroy a disk the surveyor just said carries nife.

4. **kernel/src/user/install_service.rs — nothing ties the surveyor's report to the disk the offer will destroy.** `spawn_surveyor` hands the surveyor both the target disk's endpoint and a roster of *every* virtio and PCI block device in the machine, then prints the returned flags and partition count next to "TARGET: the NVMe disk attached to this machine". On a multi-disk machine, if the table message aggregates or selects by roster order rather than describing the disk behind `disk.request`, the description attached to the wipe confirmation is for a different disk. This file never checks or documents that correspondence; it should be established (or at least asserted) here, not assumed.

5. **kernel/src/user/install_service.rs — the partition names the surveyor collects are never shown.** `F_NAMES` (and `F_ROSTER`) are defined but never read, the first report message is discarded as `_roster_msg`, and only three words of the table message are used, so the output is " (has partitions, no nife)" — it says *that* something is on the disk but not *what*, which is only half of what the proposal ("the install offer should say what is already on the disk") asks for. The unused constants also invite silent drift with `components/src/disk_surveyor.rs`.

6. **kernel/src/user/install_service.rs — the module's BUGS section is now stale.** The entry "It checks for nife and for nothing else… Naming what is already on it is `disk_surveyor`'s job, and … is the proposal for it" describes precisely the gap this commit implements, yet still reads as open future work, and the header still names only milestones 198 and 515. Since the design records are part of the deliverable, the entry should be removed or rewritten and milestone 551 recorded.

7. **kernel/src/user/install_service.rs — the EXAMPLES transcript no longer matches real output.** The documented sample still shows `TARGET: the NVMe disk attached to this machine, 1073741824 bytes.` but the code now unconditionally appends a parenthesised description (including failure strings like " (no surveyor available)"), so that exact line can never be printed again.

8. **kernel/src/user/install_service.rs — the module header and capability table still describe two programs.** The doc says "the two programs that carry it out" and "wire the two confined programs that do the work", and the table lists only `installer` and `mkfs`. The surveyor is now a third confined program holding the disk endpoint before the question is asked, and neither it, its roster page, nor its place in the safety argument are documented in the module that is the boot policy.

9. **kernel/src/user/install_service.rs — the roster frame and surveyor stack frames are leaked without the justification this module's own standard requires.** `installer_maps` leaks frames too, but it documents why at length; `create_roster_page` and the surveyor's four stack frames are allocated, granted, and never freed with no comment at all. It is a one-boot, ~5-frame cost, but the module's convention is that convenience leaks are explained.

10. **kernel/src/user/install_service.rs — `use block_roster;` is a redundant single-component-path import.** Under the 2018+ edition the file clearly uses (its other imports are `crate::…` paths and sibling crates are referenced inline, e.g. `disk_service::…`), the crate is already addressable by name, and the bare `use` trips clippy's `single_component_path_imports` while adding a second, inconsistent style of crate reference to the file.
