1. **`kernel/src/user/install_service.rs` — the "(survey timed out or failed)" fallback is unreachable, and the real failure mode is a hung boot.** `spawn_surveyor` can never return `None`: every setup failure inside it is an `.expect()` panic, and it ends with `Some(...)`. So the `else` branch in `offer()` that prints the graceful-degradation message is dead code. Worse, the two `crate::sched::ipc_recv(report)` calls have no timeout — if the surveyor thread faults, hangs, or sends fewer messages than expected, the boot blocks forever *before* the install prompt. The module's own doc header states the design guarantee: "The wait is bounded, so a stick booted on a machine with no console reaches the prompt instead of hanging." This change silently violates that guarantee on exactly the path a stranger's first boot takes, while the user-facing string claims a timeout that does not exist anywhere in the code.

2. **`kernel/src/user/install_service.rs` — the two receives assume an unchecked message count and order.** The first message is discarded without inspection (`let _roster_msg = ...`) and whatever arrives second is parsed as `(flags, partitions, nife_first_lba)`. The report format defined in this very file has an `F_ROSTER` flag bit, which implies the roster message is conditional; if it is absent, or the surveyor dies after one send, the second `ipc_recv` blocks forever (see item 1), and if the order is ever reversed the kernel formats a roster message's words as survey flags into the TARGET line. A wrong description in the one sentence whose accuracy is the entire point of the milestone is worse than no description.

3. **`kernel/src/user/install_service.rs` — `format_disk_description` never consults `F_MBR`, so MBR-partitioned disks are described as empty.** The "has partitions" branch requires `F_PRIMARY` (a GPT primary header). A disk carrying a legacy MBR partition table and no GPT — the most common Windows-disk layout — would report `F_MBR` without `F_PRIMARY` and fall through to `" (unpartitioned or unreadable)"`. The module's BUGS note says the milestone exists because "a disk carrying Windows, or a Linux root, looks exactly like an empty one from here" and a person who says yes loses that disk; this logic reintroduces precisely that misdescription for the most likely case, in the sentence whose whole job is to prevent it. (`F_MBR`, `F_BACKUP`, `F_NAMES`, and `F_ROSTER` are defined but never used.)

4. **`kernel/src/user/install_service.rs` — the in-file design record now contradicts the code, and the commit doesn't touch it.** In a tree where the docs are part of the deliverable, the module header still says under BUGS that the offer "checks for nife and for nothing else" and cites `the-install-offer-should-say-what-is-already-on-the-disk.md` as an open proposal; the EXAMPLES transcript still shows the old TARGET line with no description; and "# When the offer is made" still describes the single-survey flow. Landing milestone 551 while leaving the record describing it as unimplemented future work is exactly the class of defect no compiler will flag.

5. **`kernel/src/user/install_service.rs` — the "already has nife installed" branch is either dead or dangerous.** `offer()` returns early when the installer survey reports `R_ALREADY`, so the surveyor's `F_NIFE` description can only ever print if the two probes disagree — and in that case the code proceeds to offer to wipe a disk it is simultaneously describing as already carrying nife, defeating the documented invariant that an installed machine is never offered an install. The pre-prompt nife check should come from one probe, not two that can disagree.
