1. **`kernel/src/user/install_service.rs` — `spawn_surveyor` can never return `None`, and it can hang the boot forever.** Every failure path in it (`.expect("no budget…")`, `.expect("no frame for the block-device roster")`, `.expect("could not spawn…")`) panics rather than returning `None`, and both `crate::sched::ipc_recv(report)` calls block with no timeout — so the caller's `" (survey timed out or failed)"` fallback is dead code. Worse, if the surveyor image is corrupt or the process faults before sending twice, `offer()` hangs *before ever printing the prompt*, which breaks the module's own documented guarantee ("Returns after either, so the boot continues in every case"; "The wait is bounded, so a stick booted on a machine with no console reaches the prompt instead of hanging"). The survey needs the same kind of bounded wait the confirmation prompt has, and a real `None` path.

2. **`kernel/src/user/install_service.rs` — the surveyor's wire protocol is assumed, not checked.** The first message is discarded unread (`let _roster_msg = …`), and the second message's first three words are trusted directly as `(flags, partitions, nife_first_lba)` with no verdict word validated. Every other program this module spawns has its report tag checked before the payload is believed (`R_ALREADY`, `R_INSTALLED`, `R_MADE`), and the file's convention is to spell those wire contracts out in comments. If the surveyor sends the messages in the other order, sends only one, or reports an error, the kernel either hangs or prints garbage in what the module itself calls "the single most load-bearing sentence a stranger reads."

3. **`kernel/src/user/install_service.rs` — the module documentation, which this repo treats as deliverable, is now stale in at least three places.** The `BUGS` entry "It checks for nife and for nothing else… Naming what is already on it is `disk_surveyor`'s job, and `…the-install-offer-should-say-what-is-already-on-the-disk.md` is the proposal for it" describes exactly what this commit implements and should be removed or rewritten (and the proposal's status updated); the `EXAMPLES` block still shows the old `TARGET:` line with no description; and the "holds / can destroy" table and survey rationale don't mention the surveyor at all. The docs, the example output, and the code must move together in this tree.

4. **`kernel/src/user/install_service.rs` — nife detection is now duplicated, and the new copy is dead code.** `offer()` still runs the installer's `ROLE_SURVEY` first and returns early on `R_ALREADY`, so the disk surveyor only ever runs on disks where nife is absent — making `format_disk_description`'s `F_NIFE` branch unreachable in the normal flow and `_nife_first_lba` a captured-but-unused value. The branch is reachable only if the two survey mechanisms *disagree*, which is worse than dead code: we'd print "(already has nife installed)" and then offer to wipe it anyway. The surveyor's result should replace the installer's survey role (which the milestone's design presumably intends), or the dead branch and unused word should go.

5. **`kernel/src/user/install_service.rs` — `format_disk_description` ignores most of what the surveyor reports and misdescribes real cases.** `F_MBR`, `F_BACKUP`, and `F_NAMES` are defined but never consulted: a disk with only an MBR partition table, or a valid primary GPT with zero partitions, is reported as " (unpartitioned or unreadable)", and no branch ever says *what* the partitions are — which was the entire point of the proposal (warning the owner of a Windows or Linux disk). The final fallback, " (disk size unreadable)", is also self-contradictory, since the same line prints `{size_bytes} bytes` from `disk.size_bytes`.

6. **`kernel/src/user/install_service.rs` — a second program is now handed a writable channel to the disk before the user confirms, with no confinement argument.** The surveyor receives `rendezvous_cap(blk_ep, Rights::WRITE)` and `page_frame_cap(blk_shared, Rights::READ.union(Rights::WRITE))` pre-confirmation. The installer's survey role had an explicit, documented argument for why this was safe ("no entropy endpoint, so it cannot write a table anything would read back"); nothing equivalent is said for `disk_surveyor`, whose whole purpose is read-only and which arguably shouldn't hold `WRITE` on the shared page at all. The module's central safety claim — "the authority to wipe the disk does not exist until the answer does" — now rests on an undocumented assumption about a program this file doesn't explain.

7. **`kernel/src/user/install_service.rs` — the commit uses things the diff never adds.** It introduces `use block_roster;` (including `block_roster::capacity_of` in a const array length, which requires it to be a `const fn`), and calls `crate::virtio::count_block_devices()` and `crate::pci::count_block_devices()`, yet the PR touches only this one file — no `Cargo.toml`, no `virtio`/`pci` module changes. If any of those don't already exist exactly as assumed, this doesn't build. Similarly, `program("disk_surveyor")` only works if the component is already wired into the boot archive; otherwise every offer silently degrades to " (no surveyor available)" and the milestone is inert. Please confirm or include the wiring.

8. **`kernel/src/user/install_service.rs` — the surveyor is never told which roster entry is its disk.** It gets one disk endpoint plus a roster enumerating *all* virtio-MMIO and PCI block devices, with no ordinal or identity tying the two together; on a machine with more than one disk the description can describe a different device than the one the offer will destroy — precisely the failure mode the module's existing `BUGS` entry warns about for naming disks. The roster-building code also hardcodes transports by enumeration order, which needs a comment or a check that the enumeration matches what the disk service actually handed us.

9. **`kernel/src/user/install_service.rs` — new per-boot frame leaks with none of the required justification.** The roster page, four surveyor stack frames, and the budget region are allocated on every stick boot and never freed. `installer_maps` leaks too, but it carries a paragraph explaining why that's the cheapest honest answer; the same pattern here is uncommented. It's small and once per boot, but in a tree where every design trade-off is written down, this one needs writing down.
