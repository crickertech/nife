2. **notes/benchmarks.md** — The correction claims "the debug-versus-release argument and the 4.2x are ratios within a boot, where the calibration cancels exactly." The section's own methods line, immediately below the inserted block, says "Six boots debug, five release": a debug-to-release ratio spans two boots, each of which stored a different wrong rate, so the calibration errors do *not* cancel — the ratio carries the quotient of two boots' independent errors. If the argument is actually a comparison of two within-boot ratios, the correction needs to say that; as written it declares safe the one class of conclusion in the section that the defect could genuinely distort.

3. **notes/benchmarks.md** — "Nothing can recover the true values" is under-argued and likely wrong on the tree's own measurements. The same commit's notes/tsc-under-tcg.md establishes that under plain TCG on the aarch64 host the guest TSC *is* host monotonic nanoseconds (1000.000 MHz to within 42 ppm), and the correction itself declares the ticks column unaffected — so on that host the true nanosecond values were published all along, as ticks. If the eleven boots ran on xenon instead, the true rate is unmeasured but measurable. Either way the absolute claim needs the host named and the ticks recovery path addressed, because this paragraph is the standing guidance on how much trust to place in those figures.

4. **design/roadmap/526-the-x86-tsc-calibration-takes-the-smallest-of-several-windows.md** — The sentence "reporting the worst case rather than the mean was the instruction that mattered: by the mean, the defect was fixed at three windows and had never been very bad at one" says "mean" twice where the table and the argument require "median". The table's column is *median* (+0.36% at one window, +0.00% from three up); the *mean* of a one-sided heavy-tailed distribution is tail-sensitive and at one window would be dominated by the +884%/+1153% outliers, i.e. it would look terrible, not "never very bad". The statistic that hides the tail is the median, and the milestone's central justification paragraph has it backwards.

5. **design/roadmap/526-the-x86-tsc-calibration-takes-the-smallest-of-several-windows.md** — "An average would be a biased estimator for precisely the reason the minimum is an unbiased one" is statistically false: the minimum of upper bounds is still biased upward for any finite window count — the milestone's own table shows min-of-16 with a +0.47% worst case, i.e. still strictly high. The accurate claim is the deleted proposal's ("a sound estimator"): the minimum is one-sided and converging, not unbiased. This sentence is the recorded rationale for the shipped estimator and will be quoted.
