# Recorded against the QEMU pinned in .qemu-version. icount counts guest instructions, so the
# emulator version is part of what these numbers mean: script/qemu-check warns when the QEMU on
# PATH is not the pinned one, precisely because that is when a baseline comparison stops being
# apples to apples.
             # Updating this file is a statement that a performance change is intended and
             # understood; do it in the commit that causes the change. Checked by --check, a coarse
             # 10% tripwire (icount counts drift across builds; see notes/benchmarks.md).
#
# 2026-09-21, milestone 541 (a timed window that excludes preemption). Every row here moved, and
# two different causes are mixed in this save, which is why they are separated rather than left to
# a reader to guess at:
#
#   - `map_new` is the intended change. It masks interrupts across its timed window, so the row no
#     longer records whether a scheduler tick happened to land in 250 microseconds. Before this it
#     read 180,604 or 228,356 on x86_64 depending only on the phase an unrelated code-size change
#     left the timer in, a 26.4% swing over a byte-identical map path. It now reads the same number
#     either way. See design/roadmap/541-a-timed-window-that-excludes-preemption.md.
#   - **Every other row moved because the kernel grew**, not because anything on its path changed:
#     this milestone adds a per-core preemption counter (`sched::PREEMPTIONS_PER_CPU`) and one
#     relaxed increment in `sched::count_preemption`, and icount counts drift across builds when
#     live code is added at all (the module header in kernel/src/bench.rs says why). The moves are
#     0.0% to 0.3% and in both directions, with `spawn_reap` the outlier at +2.3% on x86_64 and
#     inside the tripwire on all three. Nothing here is a claim that a path got faster or slower.
#
# These numbers are the SECOND save of this milestone, and the first is worth knowing about because
# it is a hazard rather than a mistake. The counter began as a field on `cpu::PerCpu`, which took
# that struct from 128 bytes to 136 and so from indexing with a shift to indexing with a multiply;
# that cost 150 bytes on the riscv64 IPC fastpath and failed `script/fastpath-footprint`, while the
# increment itself cost nothing measurable. The counter now has its own array and the fastpath is
# byte-identical to before this milestone. The rows above moved by at most 0.12% between the two
# shapes, which is the point: **`script/bench` could not see a change that `fastpath-footprint`
# failed on**, so a green tripwire here is not evidence about code size.
#
